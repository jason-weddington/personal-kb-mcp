# Nightly map maintenance — REM sleep for the knowledge base

*High-level design for review. Synthesized from four argued positions and two critic passes, all re-grounded against the live personal KB and the deployed service on 2026-09-19.*

*Revised 2026-09-19 after pricing the work and reading the loop-engineering sources. Changes, each marked in place: the LLM shape classifier becomes a SQL predicate, set at the PROJECT level so an eligible project's ingested entries count; the override table gains an MCP tool pair so eligibility is an agent-assisted review; the runner becomes a purpose-built loop binary on the `harness` crate rather than `claude -p`; the two-week measurement gate is cut; and the cost is measured rather than deferred, with no prompt-cache discount on the nightly run because every night starts cold. Sources: `12-factor-agents`, the `harness-design` research corpus and its talos implementation, and the bounded-choice-cascade pattern.*

## The problem

Maps cover almost nothing. 27 active `mental_map` entries exist, spread across five `project_ref` values out of 47 — `agent-gtd` (14), `personal-kb` (9), `eval-fixtures` (2, actually test fixtures), `camera-profiles` (1), `home-network` (1). Of 3,227 active entries, **122 are reachable from any map (3.8%)** via the 149 `references` edges the graph builder derives from map bodies. `photoqueue` (120 entries), `cleanr` (194), `threat-intel` (45), `flickrasync`, `harness-design` — all zero maps. The anticipatory listener retrieves by matching chunky detail entries and resolving to the owning map, so the pointer set *is* the retrieval index, and it indexes 3.8% of the corpus.

The coverage deficit is not evenly distributed over things worth mapping, and that matters for sizing the job. Three of the four largest projects are not subject areas at all: `harness-design-research` (962 atomized PDF facts), `pdf-examples` (364, two unrelated PDF batches sharing one ref), `dispatch-performance-log` (623, an append-only run journal — every title beginning "Run: ", top tags `run`/`clean`/`integration`). Measured precisely against the eligibility predicate below, **the job is 1,051 entries across 25 projects — roughly two-thirds of the corpus is out of scope**, almost all of it the five ingest corpora (1,409 entries with zero hand-authored content between them) and the one append-only journal (624). With ~122 entries currently map-reachable, the real deficit is about 12% covered of a finite 1,051, not 3.8% of an unbounded 3,136. That reframing is load-bearing: it is the difference between a job that terminates and one that does not.

**But the read path says supply is not the only constraint, and this is the finding that reshaped the design.** `listener_decisions` holds 151 rows over 34 hours: 6 whispered, 60 declined `vote-none`, 55 `rule-b`, 24 `rule-a`, 6 `fallback-direct`. Two corrections to the framing we started with. First, `no-candidates` is **zero because that branch is nearly unreachable** — `_retrieve_candidate_maps` falls back to a direct map search capped at 5 before it can return empty, so with 27 maps it essentially always returns rows. Second, `fallback-direct` is a **reason mask, not an outcome class**: `_record_listener_decision` overwrites the granular reason for those 6 rows. So the honest reading is that 145 of 151 requests found a pointer-reachable owning map, and then **79 of 151 (52%) were killed by filters before the jury ever ran** — rule A drops every candidate whose `project_ref` equals the session's own project (24 declines), rule B drops candidates whose `operated_via` hint matches the session's operating manifest (55 declines, and those hints exist on exactly the 23 `agent-gtd`/`personal-kb` maps the hint script stamped). Of the 72 that reached the jury, 6 converted. Whisper consumption across all time: 1 of 59 on the listener surface, 7 of 2,415 on roster.

**Rule A is the fact that should change how you think about this.** Every design anyone proposed triggers nightly work on *recent session attention in a project*. Rule A then filters that project's maps out of exactly those sessions. Maps in project X can only ever be whispered into sessions in projects other than X. That is not necessarily a bug — the roster surface already pushes X's maps at session start in X, so the listener's job is cross-project surprise — but it means a new map serves two different channels with two different measurements, and the one we have telemetry for is the cross-project one.

**And the thing Jason actually complained about is none of the above.** It is that map maintenance currently requires him to remember to tell an agent to do it. Every map that exists was authored because a human decided, in a session, to author one. That is a pull mechanism for a push problem, and it has produced 27 maps in three months.

**One live data-destruction bug fell out of the grounding and is unrelated to whether we build any of this.** `KnowledgeBase.update` calls `_build_graph(entry)` unconditionally but gates `_enrich_one` on `knowledge_details is not None`; `GraphBuilder.build_for_entry` opens with `_clear_edges_for_source`, a bare `DELETE FROM graph_edges WHERE source = ?` with no `properties` filter. So **any metadata-only update permanently deletes an entry's LLM-enrichment edges and never restores them.** `scripts/set_operated_via_hints.py` POSTs `{update_entry_id, hints}` with no body, and the evidence is in the data: all 14 `agent-gtd` maps and all 9 `personal-kb` maps carry zero LLM edges, while the only two real maps outside that script's `HINT_MAP` — kb-01724 and kb-03257 — each still carry 6. Corpus-wide, entries with any LLM edges average 4.82.

## The idea in one paragraph

The KB's mental maps are a transactive-memory directory: an agent reads the map to know *where to look*, and the chunky `factual_reference` entries hold the retrievable facts. Today that directory is built by hand, during waking hours, by a human who has to decide to build it — so it covers 3.8% of the corpus and goes stale silently, because maps are decay-exempt and nobody reads them directly. REM sleep is the fix: while nobody is working, a small standing loop consolidates the day's writes into the directory. It notices which projects saw real activity, works out what topical areas those projects contain (`home-network` has a VPN cluster and a DNS cluster), and then for each area reviews, creates, and extends the map that points at it — appending pointers with glosses, creating a map where a real subject area has no owner, and filing a documentation gap where a subject area has nothing chunky worth pointing at. It touches only projects with recent activity or an accumulated coverage deficit, it writes additively under its own identity so every night is diffable and revertible, and it never asks permission to do the part that is mechanical.

## Design

The design has three pieces, and the first one is not nightly. That is a deliberate change from the brief and I want to be explicit about why: **unpointed entries are a flow and a stock, and only the stock needs a scheduler.** The flow has an interception point that already exists and fires at the exact moment the context needed to write a good pointer gloss is still in scope. In the sleep analogy this is encoding versus consolidation — you want both, and encoding is 30 lines of code.

### Loop 0 — capture-time pointer nudge (not nightly, fires on the write)

`kb_store` already prepends advisory prose to its tool result (that is how the map lint is delivered) and already runs the orphan check. Extend that seam: on any non-map store, if the new entry has no owning map, append *"This entry has no owning map. Nearest candidates: kb-XXXXX (Map: …), kb-YYYYY (Map: …). Add a pointer?"* — computed from one `graph_edges` anti-join plus a per-project kNN over `knowledge_vec`. No scheduler, no state, no LLM, no queue, no review surface. The agent that just wrote the entry is the only actor that knows why it matters, and the pointer glosses in kb-01724 — which are longer and better than the target entries' own titles — are exactly the content a nightly regenerator structurally cannot reconstruct. This stops the deficit growing and converts the remaining problem from recurring to draining.

### Activity detection — set membership, not a ranking

Two queries against the kb-core data DB alone. Both are `project_ref` group-bys over entries the KB already stores, so this needs no cross-database join and no session telemetry.

**Signal A — recent KB activity.** Projects with any `entry_versions` row (joined through `entry_id`) or any entry `created_at` inside a trailing 7-day window. Agents update the KB as they work, so a `project_ref` with no recent entries or versions means nobody has been working in that project — which is exactly the definition Jason intended, and it needs nothing beyond the entries themselves. Prefer versions alongside creates rather than creates alone: `home-network` ranked 6th on versions and 1st on creates in the same window, i.e. versions catch churn on existing knowledge that creates miss, and churn-on-existing-knowledge is precisely what a map absorbs. Cast TEXT timestamps to `timestamptz` rather than comparing strings (the `embedding_retry_queue` needed a `COLLATE "C"` pin for exactly this reason).

**Signal B — the coverage deficit.** Count of active non-map entries in the project with no inbound `references` edge from an active map. This is the only activity-independent signal, and it is what makes `cleanr` visible — 194 entries, zero maps, no writes since July, invisible to Signal A by construction.

Eligibility is `A > 0 OR B > threshold`, which folds the dormant-project case into the predicate instead of a special-case script. **Do not build an ordering on A.** Measured live, 7-day activity counts cluster tightly and move between runs — that is ranking on noise. Set membership is defensible; an ordering is not, until we have retrieval-demand telemetry (below), which is the signal that should eventually do the ranking.

**An earlier draft of this design added a third signal — distinct sessions from `whisper_telemetry` grouped by `cwd_project` — as a separate "work attention" measure resolved from the committed `.kb_project` anchor. That is cut as over-complicated.** It spans a second database (service/auth on the Pi, versus the data DB for everything else), it measures hook traffic rather than knowledge change, and it adds a signal whose only unique contribution was seeing projects with zero maps — which Signal B already covers, and covers better, because it counts the actual deficit rather than inferring it from attention. Knowledge written is the signal; session attention is a proxy for it that costs a cross-database join to obtain.

**Three further signals are excluded, and the exclusions are load-bearing.** `search_events` has no project or cwd column, no index beyond its pkey, and 676 of 702 recent rows are the listener probing itself with whole assistant turns as `query_text` and `top_score` pinned at the RRF artefact 1/61. `agent_feedback` has 2 rows. `graph_edges.created_at` is the timestamp of the last destructive rebuild of its source, not the birth of the relationship. And never rank on raw write volume: the loudest writer is `dispatch-performance-log`, an append-only journal, and it would win every night.

### Loop 1 — project cluster extraction (what subject areas does this project have)

Per eligible project, in order:

**Eligibility is a SQL predicate, not a classifier. This is a change from the first draft, which specced a cached four-label LLM classifier (`subject` / `journal` / `ingest_corpus` / `too_thin`) on `qwen3:4b`.** Three of those four labels are code-computable exactly, and a label is a *value* — so a classifier would have the model holding the pen on something the code already knows, which is the propose-reject-re-propose shape this design is trying to avoid everywhere else. Measured against the live corpus on 2026-09-19:

- **`ingest_corpus` is a join, not a judgment — and it is a property of the PROJECT, not of the entry.** `ingested_files.entry_ids` records provenance, and the corpus projects have *zero* hand-authored entries: `harness-design-research` 962 mappable / 962 ingested, `pdf-examples` 364/364, `ml-papers` 41/41, `history` 33/33, `karabiner_pro_ui` 9/9. So the test is `hand_authored >= 5` at the project level, and **an eligible project's ingested entries are fully map-eligible.** An earlier draft got this wrong by filtering ingested entries individually; Jason's correction is decisive and generalizes. `harness-design` began as a learning project and is now a production harness and a GTD dispatch engine — reference material ingested *into* a real project is part of that project's knowledge and should be pointed at. Concretely: `cleanr` is eligible and all 194 of its entries count (122 ingested), `personal-kb` all 243 (97 ingested).
- **`journal` separates on title-prefix uniformity, with a 5× margin.** Share of a project's mappable entries sharing their most common `short_title` prefix: `dispatch-performance-log` **97.9%** (611 of 624, all "Run: …"); the next highest among projects with ≥20 entries is `sample-project` at 17.4%, and the rest run from 12.5% down to 0.2%. A 0.60 threshold sits five-fold clear of both sides. Guard it on `mappable >= 20` so a five-entry project cannot trip it by coincidence.
- **`too_thin` is `count(*)` against a floor.**

The predicate is `hand_authored >= 5 AND NOT (mappable >= 20 AND top_prefix_share >= 0.60)`, and when measured it admitted **25 projects, 1,051 entries, 186,170 tokens** at the working packing (a **snapshot**, not a constant — the live endpoint returned 24 on 2026-09-21, because the predicate is a function of entry counts and title shapes and a project leaves the set whenever its corpus grows into a journal shape; the cost figures below move with it, though by a project at a time rather than materially) — leaving roughly two-thirds of the corpus out of scope before a single API call, almost all of it the five ingest corpora (1,409 entries) and the one journal (624).

**What remains is a human verdict, not a model's, and it goes in an override table.** Roughly five refs the code cannot call, and one it calls *wrong*: `harness-design` (71 mappable, 0 ingested, 66 distinct title prefixes) passes every gate as a subject area, but it is a dated session journal with a reading order and no topical partition — the uniformity test misses it precisely because its titles vary. Also genuinely ambiguous: `aws-agent-gotchas` (36, a cross-cutting lesson collection with no repo), `ai-coding` (33), `agent-gtd-dev` (10, probably an alias of `agent-gtd`), and `threat-intel`, which sits at exactly the floor with `hand_authored = 5` of 45. So keep the editable row — a wrong call should be one write, not a redeploy — and delete the model that was going to populate it. The override must beat the computed verdict in **both** directions, since `harness-design` needs forcing *off* and a future project may need forcing *on*.

**The override table gets an MCP tool pair, because that is what makes it a review surface rather than a schema.** A read tool returns every project with its evidence — mappable, ingested, hand-authored, top-prefix share, the computed verdict and any override — and a write tool sets or clears one override with a reason. Jason's framing is the design rationale: *manual map maintenance* fails for the reasons this whole document exists, but *periodically checking which projects deserve maps* is an easy review task, and it is exactly the shape an agent-assisted review handles well. Returning the evidence rather than a bare boolean is load-bearing — a reviewing agent that cannot explain why a project was excluded cannot help decide whether the exclusion was right.

**Pocket detection, not clustering.** The primary trigger is one precise mechanism: *a dense, mutually-nearest group of entries that no active map references.* One indexed `graph_edges` anti-join plus one per-project kNN over `knowledge_vec`. It needs no `k`, it is precision-first by construction (it cannot propose a map for a region already covered), and it produces the right answer on the one fully worked example: kb-03211/12/13/14, created within 60 seconds of each other, the tightest mutual-nearest group in `home-network` (0.795/0.635/0.599/0.577), unpointed, sitting under a v9 map. Note `knowledge_vec` has **no ANN index** — every kNN is exact brute force over 1,024 dims — so this is fine per-project and must not run in the service event loop.

**Naming by model, because geometry provably cannot do it.** Hand the model the project's non-map entries as `id | short_title | entry_type | tags`, the existing maps with their pointer sets, and the detected pockets. It names the areas, merges, splits, rejects, and may return "this entry belongs nowhere" (kb-03238 sits in `home-network` with 0.399 max similarity to anything in it — forced assignment is a defect). Two methods are excluded on measured evidence: thresholded connected components collapse outright (`cleanr` → components of [172, 6, 2] out of 180 at cosine ≥ 0.62; `harness-design` → one component of all 67), and k-means separates cleanly but *choosing k is the entire problem* — k=10 on `cleanr` over-split Flickr into three near-duplicates, which is exactly the mechanism that manufactures redundant churning maps. Most decisively, **Jason's own VPN/DNS example is not in the vectors**: kb-01722's four nearest neighbours are three DNS entries and a NAT entry, because geometrically and causally those entries are one topic ("how does a packet reach a service here"). VPN and DNS are *names a human applies*. Tags recover the split only because tag authorship already encoded that intent — which makes tags a strong feature and a bad partition key (`allowlist`:11 beside `allow-list`:9, `threading`:8 beside `multithreading`:4).

Overlap is expected and correct, not a defect to resolve: `home-network`'s kb-03215 and kb-03217 genuinely belong to both VPN and DNS, and the graph already carries 17 details with two owning maps, 2 with three, 2 with four.

### Loop 2 — map review, create, maintain (closed op vocabulary)

The output is **a patch from a fixed vocabulary, never a body**: `create_map`, `add_pointer(map, detail, gloss)`, `strike_gap(gap, closing_entry_id)`, `propose_gap`, `author_detail` (hand off to `author-chunky-entries`), `flag_orphan`, `flag_stale`. There is no `rewrite_body` op. That is the point — a closed vocabulary recorded in a schema is enforceable; "please don't rewrite the prose" in a prompt is not, at 3am, with nobody watching.

This vocabulary is derived from what human maintenance actually looks like, not invented. kb-01724 has nine versions and the change reasons are unambiguous: v2 "Add kb-01858 pointer", v3 "Add pointer to kb-02921", v5 "Add pointer to kb-02940", v6 "Add pointer to kb-03215". **Every substantive revision is an append of one pointer with a one-line rationale.** Two of the nine are pure lint repair. Nothing is ever a rewrite.

And what a rewrite would destroy is the map's actual value. kb-01724's second paragraph is negative knowledge about reader misconceptions — "assuming some host terminates the VPN (it does not; the router does)… treating a VPN-connected laptop as proof of LAN reachability" — derived from a human having been wrong, and not recoverable from the bodies of the entries it points at. kb-03257 sequences eight pointers with a per-step reason: that is a reading order, which is pedagogy, not content. The "Not yet documented" line is the loop's own work queue, and an agent cannot *derive absence* — so it will either silently delete the queue or fabricate a gap, and a fabricated gap dispatches a real authoring run at a subsystem that does not exist. Hence gaps are append-and-strike-only, and a strike requires citing the entry that closed it.

**One implementation constraint the op vocabulary must absorb.** Because `_build_graph` runs unconditionally while `_enrich_one` does not, a metadata-only patch would destroy the target's enrichment edges. So every automated write **carries the full `knowledge_details`** as a read-modify-write, and the guarantee moves from "we never hold a body" to "we diff the body we wrote against the body we read and reject anything but an append." That diff-shape validator is real work and it is the honest price of doing this safely.

### What runs where, and which model tier

| Piece | Host | Why | Model |
|---|---|---|---|
| Capture-time nudge (Loop 0) | kb-service, in request path | SQL + kNN over one project; must fire synchronously with the store | none |
| Eligibility + deficit detection | kb-service, systemd `.timer` + CLI subcommand | SQL only, no inference, needs journald + `systemctl start` as a free "run it now" | none |
| Pocket detection (kNN) | off the Pi — desktop or r7 | No ANN index, exact brute force, 4-core aarch64 Pi 4 serving live requests | none |
| Naming (Loop 1) and op authoring (Loop 2) | purpose-built loop binary, on the kb-service host | See below | Sonnet, direct Anthropic API |
| The write | kb-service HTTP, machine API key | Server-side gates are only enforceable on this path | — |

**The runner is `somnus`, a purpose-built loop binary on the kb-service host, not `claude -p` anywhere. This supersedes the first draft's `dev-desktop` recommendation and its reasoning.** The earlier argument was correct about the dispatch fleet — no `~/.claude/workflows/` on any dispatch host, and `prepare_workspace` runs `git clone` with `check=True`, so a dispatch for a repo-less project dies before Claude ever launches — but it then reached for Claude Code as the runner, and Claude Code is the wrong tool here. It does not run well on an 8GB Pi 4, and everything it provides beyond the model call is something this loop does not want: a general tool surface, a conversational context that grows, and a harness whose termination condition is a human closing the session.

What the loop actually needs is small, and once the read path is pre-fetched (below) it needs no filesystem, no repo clone, no MCP server and no workflows directory — only outbound HTTPS to the Anthropic API and to kb-service. That makes the correct host **the Pi already running kb-service**, where the machine API key and the DB pool already live, rather than the box Jason works on. Follow talos's deployment pattern: cross-compile or build elsewhere and have the Pi pull a prebuilt binary, immutable per version token, rather than building on a Pi 4.

**No LLM inference inside the kb-service event loop**, beyond what the listener already does. The Pis are 4-core aarch64 Pi 4s, the data DB is not even on them, and three Pis share one data DB (which is why the `embedding_retry_queue` lease exists — copy that pattern, don't invent one, and only if a manual run could race the timer).

### Build, delivery and ownership — settled 2026-09-19

Agreed across three sessions overnight, so the seams are recorded here rather than living in anyone's conversation.

**The binary is `somnus`, a crate in the `harness-design` Cargo workspace consuming `harness` as a path dependency.** Placement is not cosmetic: a `crates/` sibling inherits the workspace lint table, the shared dependency versions, the toolchain pin (1.96.0) and the cross-compile setup, and — decisively — the existing aarch64 publish pipeline. Standing up a second release path to avoid a directory was the bad trade. Inheriting the workspace properly requires the path in root `members`, `version`/`edition`/`license`/`authors` as `.workspace = true`, per-dependency `foo.workspace = true`, and an **explicit `[lints] workspace = true` table** — Cargo does not inherit lints implicitly, and without that line the crate silently loses `unsafe_code = "forbid"` and the pedantic clippy set. `cargo sort --check` is a commit gate, so dependency tables stay alphabetised.

**Publish and consume are separate, and that is the whole contract.** The harness-design session publishes every workspace binary in **one invocation at one token** to `artifact-host:/srv/talos/<token>/<arch>/<binary>`, with `/srv/talos/latest` holding the token on one line, served over that host's Caddy. The token is `git describe --tags --always --dirty`, stamped by `build.rs` and read back through `<binary> --version` — not the Cargo version. Publishing both binaries together is what makes a single `latest` file honest and dissolves the directory-level immutability trap, because there is never a second later upload at an existing token.

**Each session owns delivery to its own hosts.** Jason's rule: *every session owns its own release tooling and process.* The agent_gtd session delivers talos to the dispatch fleet because it knows when that is safe; this project delivers `somnus` to the KB hosts for the same reason. An earlier proposal to teach one installer a binary name and a host set was rejected — it would have deduplicated a mechanism at the cost of coupling three sessions' release timing, and it would have put the decision *is it safe to deploy right now* in the hands of whoever happened to be running rather than the session holding the constraint. Two independent consumers of `latest` with independent timing is the intended shape, which means **the two host sets can legitimately run different tokens** and nothing may assume fleet-wide version uniformity.

**Two obligations this places on the binary**, both cheap now and expensive later: `somnus --version` must emit the **same output shape** as `talos --version`, because an installer's skip logic parses field 2 of it to read the installed token, and a binary without it turns every update into an unconditional reinstall. And whatever records "the installed token" must be **per-binary** — a shared notion lets one binary's presence suppress the other's install, which is the silent-skip failure one level down.

**A consumer must verify the artifact exists at the resolved token before installing, and fail loudly rather than fall back.** `latest` is a bare token with no binary name, so resolving it trusts an invariant the publish script alone enforces. A silent downgrade of an unattended nightly maintenance loop is worse than a loud failure.

### Workflow reuse, honestly scoped

`author-chunky-entries.workflow.js` is directly reusable and needs no change in kind: its `{key, name, responsibility, scope_paths, gaps}` subsystem input is exactly what a cluster spec serializes to, and it is the right consumer of the gap list — a map cannot point at a detail entry that does not exist.

`recommend-maps.workflow.js` is **half** reusable. Its phase shape (multi-lens discovery → canonicalize → per-seam recommend → synthesize) and its grounding discipline (`build_now` only when a real pointer entry was found; "NEVER invent a kb-XXXXX id") are exactly right and should be kept. Its *mechanism* is not: all four lenses read code at `repoPath`, which is structurally wrong for `home-network`, `threat-intel`, `cleanr`, `dispatch-performance-log` and everything else without a repo, and it is whole-project rather than incremental — nightly it would re-derive the full seam list and collide with maps that already exist. Swap the four code lenses for KB lenses over titles, tags, and unowned pockets, and add an input for "here are the existing maps, leave them alone." Also: line 23 of that file asserts "A map with zero pointers is rejected on store," which is **false on the update path** — fix the string, it is currently teaching agents an invariant the code does not enforce.

### The loop harness — thin inner, real outer

Informed by `12-factor-agents`, the `harness-design` research corpus and its shipped talos implementation, and the bounded-choice-cascade pattern. **The headline finding is that this is barely an agent loop, and that is a feature.**

**Apply the cascade, and the map body stops being the model's to write.** The map-purity lint — which rejects file paths, `ENV_VAR` tokens, dotted identifiers, quoted literals and slash-joined path-shaped tokens — is structurally the same thing as the eleven validators in the Grit Mile plan generator: a set of code-computable rules policing values a reasoner proposed. Let the model emit a map body freely and you have guaranteed a propose-reject-re-propose loop against that lint, at 3am, with nobody watching. So invert it exactly as the cascade prescribes. The canonical map form has four parts — two or three sentences of fact-free orientation, one coarse `Lives in <package/dir>` line, a `Detail entries:` pointer list, and a prose `Not yet documented:` line — and **code composes three of the four.** The orientation prose is the only free text the model ever writes, and it is the one part that carries genuine judgment, which is what keeps this from being the parrot. Every token class the lint rejects can only arise in the three code-composed parts, so **the map is born lint-clean by construction** and the lint has nothing left to police but the orientation prose and the per-pointer glosses. That deletes "anything that failed the lint twice goes to review" as a live path rather than handling it.

It also fixes the length budget, which is a latent defect in the current advisory lint (see Guardrails). Because code owns the structural lines and the model writes only prose and glosses, the budget decomposes naturally: a fixed allowance for the orientation, a per-pointer allowance for each gloss. A map that is long because it points at twenty things is healthy; a per-map character cap cannot tell that apart from sprawling prose, and enforcing one would strip the glosses out of the best-covered maps.

**Enforce that split with write authority, not with prompt text.** The single best mechanism in the talos design is that there is no `set_verified` tool: the per-criterion state machine runs `NotStarted → InProgress → ClaimedDone → Verified` and only the harness writes the last transition, so the agent literally cannot type `Verified` into the record. The analogue here is that **there is no `write_map` tool.** The model emits ops from the closed vocabulary; the harness materializes the body and POSTs it. This matters because the one measured experiment in that corpus on fixing behaviour with prompt rules came back negative — per-criterion prompt rules produced *no behavioural change at all* on their target failure shape — and its transferable rule is blunt: for a prompt or loop change, measure the behaviour the change should induce before claiming any outcome. A closed vocabulary in a schema is enforceable. "Please don't rewrite the prose" is not.

**Pre-fetch the whole read path, then the loop collapses.** Everything the model needs is known before the first inference: the project's eligible entries, its existing maps, their pointer sets, the detected pockets. 12-factor's factor 13 says to fetch that deterministically and synthesize the call-and-result events into the thread, then delete the corresponding read tools from the output union. Do that and two things follow. The model cannot wander the KB, and the unit of work becomes **one inference**, not an agentic tool-calling loop. Measured packing confirms it fits: titles plus tags plus a 600-character excerpt across all 25 eligible projects is 186,170 tokens, so the largest single project (`personal-kb`, 243 mappable entries) packs to roughly 43k — one comfortable call against a 200k window. So Loop 1 is one inference per project and Loop 2 is one inference per cluster. The loop machinery exists for the steer-and-retry path only.

**The real loop is the outer one.** It is Ralph-shaped, and REM sleep satisfies all five of that pattern's stated requirements: monotone external state (pointer coverage, additive-only by design), a prompt that is a pure function of that state (one SQL query), a cheap unambiguous stop-oracle (the unowned-cluster query returns zero rows), progress durable outside the context (the KB itself plus the cluster/decline ledger), and units that fit one inner budget (one cluster, one op). One genuine mismatch: Ralph reverts a bad iteration with `git reset --hard` to the last green commit, and there is no analogue when the write target is a live Postgres. The additive-only invariant, the edge-superset check and the per-night caps are what substitute for revert, which is why they are non-negotiable rather than nice-to-have.

**Termination is claim-verify, three legs.** Leg 1, the model called `finish`. Leg 2, the gate is green — and the gate is the `run_checks` analogue: server-side hard lint plus the edge-set superset invariant plus the append-only body diff plus the orphan check, returning failures with reasons rather than a pass/fail bit. Leg 3, something demonstrably changed: the project's pointer count moved. Leg 3 exists because without it a run that touched nothing can claim a fully verified Done on a corpus that was already consistent; answer mode in talos gets read-only enforcement by inverting this same primitive, and `already_satisfied` here is the same inversion — unchanged state plus a mandatory reason. **The harness never fabricates Done.** A green gate with no claim terminates `failed` while recording the recovery facts (gates green at exit, what the ops would have been), because gates are not guaranteed to be a superset of the intent.

**The disposition taxonomy already has a slot for the hardest case.** talos discriminates blocked from failed by asking whether running the same thing again has any chance of working — no means blocked, maybe means failed. `propose_gap` is exactly blocked: the cluster is real, nothing chunky exists to point at, and no amount of retrying fixes that because it needs an upstream authoring run. That is a clean mapping, not a forced one.

**Durability: never re-execute, don't checkpoint cleverly.** Write `ToolCallStarted{seq, name, args, call_id}` to an append-only log *before* the HTTP write and `ToolCallResult` after. On resume, a started event with no matching result is an interrupted call: pair it by `call_id`, synthesize an `is_error` result, and **never re-execute it** — the write may already have landed. This is stricter and cheaper than the idempotency key the 12-factor material leaves you to invent for yourself (that corpus gives you resumability but never says the word idempotency), and it is already implemented. One test note carried forward from an adversarial review that found a real bug in exactly this code: exercise crash reconciliation with **at least two** interrupted calls, because a single-call proof is where wrong coincides with right.

**What not to build, each for a measured reason.** No compaction: the highest context-window fill ever observed on real work in that corpus is 80.1%, every large-window run sits at 7–20%, and a per-unit context here is ~11k tokens — meanwhile a compaction predicate bug once fired on 100% of 3,061 turn transitions at ~1% occupancy and read as heavy pressure in telemetry. No finish-recovery nudge: it logged zero rescues in 112 trials once the iteration cap was generous, because stalled runs sit on a red gate rather than a green one. No lease until a manual run can actually race the timer; no run table; no five-stage DAG; no LSP or anything else resident on the Pi.

**The one thing talos deferred that this loop must build: the cost accumulator.** Token and cost caps are unbuilt there, and the stated reason is that production dispatch runs on a prepaid open-weights lane — that reason does not transfer to a metered Sonnet loop. Accumulate `input_tokens + cache_creation_input_tokens + cache_read_input_tokens` per call (the first field is the *uncached remainder only*, and treating it as the total has already broken one trigger in that corpus), price it, and enforce at the same end-of-iteration seam wall-clock already uses.

**Prompt caching is the highest-leverage lever and it fails silently.** The stable prefix is the op vocabulary, the lint rules, the canonical map form and the project's map roster; one breakpoint on the system block covers the tools that precede it, plus one rolling breakpoint on the last block of the last message. Order every serialized map with `BTreeMap`, never `HashMap`, and keep timestamps, run ids and UUIDs out of the prompt — each is a silent invalidator. Then verify: read `cache_read_input_tokens` on every response and alarm if it stays zero across same-prefix turns. An interactive user notices cost spiking; an unattended nightly loop does not. In this corpus a caching-accounting bug made every recorded cost figure an upper bound for months.

**Build on talos rather than starting a new harness. Verified against the code on 2026-09-19: this is a tool set plus a gate adapter, not a fork.** It already has the bounded inner loop, the run record with its durable/disposable split, a SQLite store behind a three-method trait, claim-verify, crash reconciliation, prompt caching, an Anthropic backend, and deterministic backoff on classified-transient errors only. The three extension points check out:

- **The tool set is fully pluggable.** `engine::run` takes `tools: &ToolRegistry` as a parameter — `RunConfig` has no `tools` field at all — and the registry holds `Arc<dyn Tool>` over an object-safe, `async` trait whose result type carries nothing file-specific. The eight built-ins live in one *optional* helper (`standard_registry`) that a library consumer need never call. The system prompt's tool list is derived from whatever was registered. Register `FinishTool` explicitly, because it is how the loop terminates.
- **A run works with no git repo.** `observe_tree` returns `Unobservable` for a non-repo, `classify_change` fails open on either side, and the engine warns on stderr and continues. The fail-open is deliberate and pinned by a comment and a test: *a workspace the harness cannot observe is no evidence that work did not happen.* `Workspace` needs only an existing directory; confinement is lexical, with no git dependency.
- **`harness` is a real library crate.** Every module is `pub`, it is consumed by the `talos` binary as a path dependency, and four in-repo examples drive the loop from outside the CLI. `ralph.rs` is the precedent for a second single-purpose loop layered on `engine::run`.

**THE GATE IS MANDATORY, NOT A WORKAROUND — and this is the single most important constraint in this section.** Verified with the harness-design session: with `checks = None` **and** a non-git working directory, leg 2 and leg 3 both go **inert** — `Verification::NoChecksConfigured` plus `ChangeEvidence::Unobservable` — and a `finish(done)` is accepted purely on the model's word. That is the three-legs contract collapsed to one leg, and **it is the exact default configuration this workload lands in.** So the gate is not a nicety to be deferred to a later phase; without it the loop has no mechanical verification whatsoever and every guardrail in this document reduces to a prompt instruction.

`RunConfig.checks` is `Option<ChecksRunner>`, a concrete struct with private fields that spawns a subprocess — there is no `dyn Gate` seam, no closure, no trait. So the validation endpoint is expressed as a command whose exit code is the verdict, `/bin/sh -c 'curl -sf -X POST …'`, which `shell_checks_runner` already builds and for which `curl -f` already gives the right exit semantics. Register it under the name `run_checks`, because the engine keys several heuristics off that literal tool name. Doing so restores leg 2 as genuine harness-enforced verification. Leg 3 stays inert, covered by an assertion inside the loop's own `finish` tool — which is agent-adjacent rather than harness-enforced and is therefore the weakest part of this design, to be named as such rather than glossed.

**Leg 3 cannot be supplied by a consumer today, for two reasons not one.** The `baseline_override` threaded through the internal loop is not a `RunConfig` field and is `Some` only on the resume path; and more decisively, the finish path **re-observes the current tree unconditionally**, so supplying only a baseline would compare real evidence against a freshly-shelled `git status`. Both sides would have to be injectable. The harness-design session captured the proper fix as a change-evidence provider on `RunConfig` consulted for both observations, defaulting to `observe_tree` so filesystem consumers see no change — tracked as their `c4d4b476`. Until it lands, the fallback stands.

**The system prompt has exactly one non-forking route, and it is free.** There is no `RunConfig` field, no builder, no env var and no template-directory override; the template is compile-time bound. The supported route is to **implement `ModelBackend` as a wrapper and rewrite `TurnRequest.system`** — its fields are public and talos already implements that trait externally, so this is a sanctioned shape rather than a hack. It must be byte-stable per run or it breaks the prompt-cache invariant. This costs nothing extra because a wrapper is needed anyway: `engine::run` takes `&impl ModelBackend`, a sized generic, so `Arc<dyn ModelBackend>` cannot be passed and a newtype is required regardless. Two frictions, one wrapper.

**Run it in build mode, not answer mode, and the reason is a scope boundary worth stating.** Answer mode is the obvious-looking fit — its verifier is a JSON schema over the `finish(answer)` payload rather than a shell command, which sidesteps the gate friction entirely. It is the wrong choice, because answer mode enforces read-only by requiring the tree to be **unchanged**, and that postcondition is scoped to the *filesystem*. An agent whose tools are HTTP calls into a Postgres-backed KB leaves the tree pristine while rewriting map bodies, so it satisfies the precondition perfectly while doing exactly what the precondition exists to prevent. The guarantee is not weakened here; it is void for this tool set. Running REM sleep in answer mode would put a "read-only" label on the most write-heavy thing in the system. (Generalizes for anyone hosting non-filesystem tools on that harness: leg 3 measures *filesystem* evidence, and its inversion in answer mode is a filesystem read-only guarantee, not a general one.)

**One trap to pin before anyone builds this.** The `finish(done)` precondition rejects `TreeUnchanged`. An HTTP-only agent changes no files — so if the loop's working directory ever *is* a git repo, **every `finish(done)` is rejected and every run burns to `max_iterations`.** The non-git working directory is therefore load-bearing, not incidental. Set it deliberately and assert it at startup.

**Finish-recovery must be disabled from a named constant, not a literal, and the reason inverted on inspection.** The first reading was that `last_gate_green` is set only by `run_checks`/`edit_file`/`bash` *by name*, so an HTTP tool set could never arm the nudge. That is wrong once the gate is mandatory: registering the shell-out gate as `run_checks` *does* set it. What stays permanently false is `tree_dirty`, which only `edit_file` and `bash` set — so the nudge's "tree static for K iterations" predicate is **always true**, and the nudge would arm the moment the gate first goes green. For a loop that legitimately keeps working after a green gate, that is a false nudge on structural grounds rather than a dead mechanism. Disable it — but the harness-design session has filed the `last_gate_green`-set-by-one-tool behaviour as a defect (their `1b651ed6`) after it destroyed a complete gate-green run in which the agent had verified via `bash` and the harness never saw it. If that fix lands the nudge becomes live for tool sets like this one, so the disable belongs behind a flippable constant rather than a literal `0`.

### Leg 3 is real now, and its error path is the design decision

The harness-design session merged the change-evidence seam (`harness-design` `046b1f9`), so leg 3 is no longer a fail-open placeholder: `RunConfig::with_change_observer(Arc<dyn ChangeObserver>)` supplies a custom observer, it serves **both** the run-start baseline and all three finish-time observations, and `TreeObservation` is publicly constructible. The loop's observer returns the KB's pointer count. Two inherited oddities, both cosmetic: the evidence field is called `porcelain` and some rejection messages say "working tree" — the git-flavoured names were kept deliberately rather than rippling a rename through transcript rendering, so note the reason at the construction site before someone "fixes" it.

**The load-bearing choice is what the observer returns when it cannot observe, and it must fail CLOSED: return the cached run-start observation.** Verified against `classify_change`, which compares `porcelain` *and* `head` by whole-value equality. Returning the exact cached baseline therefore yields `TreeUnchanged`, which the finish path rejects — so a loop that cannot prove work happened does not get to claim it did. The observer holds that cached value itself, which is possible only because it is a long-lived `Arc` rather than a stateless function. If the *baseline* fails at run start, refuse to start the run; that is the one place a hard failure is cheap.

**Every simpler option fails open, and one of them manufactures a false positive.** Returning `Unobservable` on error is the fail-open this seam exists to remove. A sentinel value is *worse*: with a baseline of `"17"` and a finish observation of `"OBSERVE_FAILED"`, the two differ and `classify_change` reads `TreeChanged`, asserting evidence of work nobody observed. The same trap applies to `head` — an error marker there differs from the baseline just as fatally. **There is no field available for signalling "I failed" without breaking the equality the fail-closed property depends on.** The asymmetry settles it: a refused Done costs one wasted night, a falsely accepted one silently corrupts a directory nobody reads directly.

**Which leaves a diagnosability hole the observer must close, because the harness structurally cannot.** A `no_change` rejection does **not** terminate the run — it feeds a message back to the model and the loop continues. So a sustained Postgres outage plays out as attempt, error, cached baseline, `TreeUnchanged`, reject, retry, until the iteration cap, and the terminal reads *"the agent kept claiming done with no changes"* while the real cause is invisible. At 3am that is a misleading diagnosis pointing at the model instead of the database. The trait returns only a `TreeObservation` and has no error channel by design, so the mitigation belongs to the observer: **log loudly to stderr and to the loop's own telemetry on every fallback, and count CONSECUTIVE fallbacks so the log escalates** — one is a blip, ten in a row is an outage, and the harness cannot tell them apart even though the operator must. `stats.no_change_rejections` on the run record is a weak corroborating signal and does not name Postgres.

Bound the observe call at **10s**, tighter than the trait's 30s guidance: it is one indexed count against Postgres on the same Pi, so a query that cannot answer in ten seconds means the KB is unhealthy and waiting longer only delays a refusal that is coming anyway. Confirm the provider was actually used by reading `run_start.config.change_observer`, which records `"git"` or `"custom"` — a silent fallback to the filesystem observer is otherwise undetectable.

**Keep the run store on local SQLite.** `StoreError` is SQLite-shaped (`Sql(rusqlite::Error)`, `Serialization`, `Join(String)`, `LockPoisoned`), so an HTTP-backed `RunStore` has no honest error variant and would have to stuff service failures into `Join(String)`. That friction is avoidable rather than inherent: the run record is the *loop's own* durable state, not KB data, and the loop runs on the same Pi as kb-service, so a local SQLite store is both the natural fit and what the error type was designed for. Only the KB writes go over HTTP.

### What it costs — priced, not guessed

Measured against the live corpus, Sonnet at $3/$15 per Mtok. The eligible corpus is 1,051 entries across 25 projects: 50,600 tokens as titles-and-tags only, **186,170 tokens** packed as titles plus a 600-character excerpt, 434,161 tokens at full body.

| | input | output | cost |
|---|---|---|---|
| **Backfill** — Loop 1 over 25 projects, two passes | 447k | 60k | $2.24 |
| **Backfill** — Loop 2, ~85 clusters (~60 new maps, 25 reviewed) | 510k | 43k | $2.17 |
| **Backfill** — lint-repair retries, assume 30% | 190k | 15k | $0.80 |
| **Backfill total** | | | **≈ $5.20** |
| **Nightly** — 3 projects × ~11k, plus 1–2 map rewrites | 33k | 3k | **$0.15** |
| **Monthly steady state** | | | **≈ $4.50** |

Steady-state volume is measured, not assumed: 69 new hand-authored entries in eligible projects over the trailing 14 days, i.e. ~5/day and ~3,840 tokens/day of new material touching ~3 projects a night.

**Prompt caching is worth almost nothing to the nightly run, and an earlier draft of this table wrongly discounted for it.** Every nightly run starts with a **cold cache** — the gap between runs is 24 hours and the TTL is five minutes, or an hour at a 2× write premium. So caching pays only *within* a single continuous run: it is a real discount on the backfill, and on the two or three projects that share a global prefix inside one night it saves on the order of a cent. The nightly figures above therefore assume **no cache benefit at all**, which is the honest model. Keep the cache-hit assertion in the guardrails regardless — it is there as a *correctness* instrument for the backfill, where a silent invalidator would actually cost money.

One volume caveat the measurement hides: ingestion is **bursty**. A batch ingest into an eligible project lands dozens of entries at once, so that night's run is an outlier rather than a $0.15 night. The per-night cost ceiling is what keeps that bounded.

**Three consequences.** First, **do not build the Ollama lane** — not because it is complex, but because at under $5/month cost is not the deciding variable, and naming subject areas is exactly the sparse high-judgment rung the cascade says to spend the good model on. Keep the backend behind one `complete(messages, schema) -> obj` port so switching is a config change, and note the honest counter-argument: the Ollama Max credits are already paid for and do not roll over, which is an argument for *measuring* a cheap lane against a fixture set, not for building it speculatively. Second, **a ~$5 backfill removes the need for incremental state** — at that price the full recompute is re-runnable whenever the prompt changes, so build full-recompute first and add incrementality only if a night gets slow. Third, budget **~$50 for the whole build-and-tune cycle** including a dozen backfill re-runs while the prompt is in flux.

The rule, in one sentence: **the loop may add; it may never subtract or rewrite prose a human wrote.**

Operationally, three tests, all of which must pass for an unattended write:

1. **Additive on the body.** The post-write body contains the pre-write body as a contiguous-block-preserving superset. New lines may be appended, existing lines may not be altered — with the single exception of striking a "Not yet documented" item, which requires citing the entry that closed it.
2. **Non-decreasing on the graph.** The post-write outbound edge set is a superset of the pre-write set. Note this must be checked on the **whole edge set**, not the `kb-XXXXX` pointer ids — a pointer-id superset check passes cleanly while five `related_to`/`uses`/`solves` enrichment edges vanish.
3. **Authorship-tiered.** A map whose `contributor` is the machine principal is the loop's to edit, including its prose. A map authored by a human is append-only, permanently.

Unattended: `add_pointer` with a gloss, `create_map` for a pocket with at least two real chunky targets, `strike_gap` with a citation, `propose_gap`, `author_detail` dispatch, and prose edits on machine-authored maps. **Never unattended: writing an eligibility override.** That row is the human verdict the predicate cannot produce, so the loop reads it and never writes it — a loop that could force its own eligibility has no gate at all. Needs review: any prose edit to a human-authored map, `flag_stale`, `flag_orphan`, any `project_ref` change, anything that failed the lint twice, and any map that trips the churn brake.

Never, by either: `deactivate` (on the HTTP path it runs `DELETE FROM graph_edges WHERE source = ?`, instantly orphaning every detail that map owned from the listener's reverse lookup), pointer removal, and any touch of `NULL`-`project_ref` entries (105 of them, invisible to every per-project query, yet already pointed at by maps — 2 of kb-01724's 11 pointers leave the project, one to `blog` and one to a NULL-project entry, and a per-project loop must never be positioned to remove what it cannot see).

**The trust boundary is not a review queue.** A queue Jason does not drain converts an automation gap into a triage gap, which is the exact thing he asked us to delete. The review lane exists, but it is a digest he reads when he feels like it, and nothing in the unattended lane blocks on it. The design's bet is that the additive lane covers most of the recoverable value — and the measured data supports it: 7 of `home-network`'s 17 detail entries are unpointed under a *v9* map.

## Guardrails

**Cheap and mandatory — ship these regardless of whether the loop is ever built:**

- **Orphan check on the UPDATE path.** `_check_orphan_mental_map` runs on create (`kb_write_routes.py:199`) and per-batch-entry (`:282`), and the update branch (`:221-247`) has none. Maintenance *is* update. Prevents: an update silently stripping a map to zero pointers, returning 200, and orphaning everything it owned.
- **Full-body writes on every automated update.** Prevents: permanent, silent deletion of enrichment edges (already done to 23 of 27 maps by the hint script). Also repair the 23, by a no-op re-save of each body, which re-runs both `_build_graph` and `_enrich_one`.
- **Edge-set superset invariant** on every automated map write. Prevents: a regenerated or re-derived body deleting edges the listener's reverse lookup joins on, while a pointer-id check passes.
- **Server-side hard lint for the machine principal — but budgeted PER POINTER, not per map.** `lint_map_body` exists only in the MCP client, only as prepended advisory prose whose own docstring says it never signals rejection, and `grep` for it under the service `src/` returns nothing, so an HTTP-writing agent gets zero purity feedback. Prevents: a nightly agent persisting a map body full of paths, `ENV_VAR`s and dotted identifiers. The *purity* rules stay as designed with no relaxation, and gated on the principal rather than globally.

  **The ~1,500-char length guideline, however, is a latent defect and must not be promoted as-is.** It does not scale with pointer count, and the failure mode is specific and severe: a map with six pointers orients comfortably in 1,500 chars, but the same map with twenty cannot if each pointer carries the one-clause reason that makes it useful — and those reasons are exactly what this design forbids a machine from regenerating. A hard per-map character cap would therefore mechanically strip the glosses out of precisely the maps that have earned the most pointers, inverting the design's own intent. The evidence is live and it moved while this document was being written: kb-03257 went from 6 pointers at 1,578 chars to 13 pointers at ~2,540 chars, tripping the advisory twice, and its author correctly stopped cutting rather than delete glosses to satisfy a number. kb-01724 sits at 2,319 chars across 11 pointers for the same reason. (Credit: the camera-profiles session surfaced this while authoring those pointers.)

  So the budget is compositional, which falls out of the body being code-composed anyway: a fixed allowance for the orientation prose, plus a per-pointer allowance for each gloss, plus whatever the code-generated structural lines cost — measured per component rather than summed and capped. The purity rules apply only to the prose and the glosses, since the structural lines are the only place paths and dotted identifiers legitimately appear and code emits those in the sanctioned form. A map that is long *because it points at twenty things* is a healthy map; a map that is long because its orientation prose sprawled is not, and only a per-component budget can tell those apart.
- **Never deactivate a map.** Prevents: one call orphaning a dozen details.
- **Dedicated machine API key** so `contributor`/`updated_by` identify the loop. Prevents: nothing directly — but it is the enabling primitive for revert, metric segmentation, the authorship tier, and "show me everything the robot did last night," each of which becomes one predicate.
- **Hard cap: one new map per project per night, three per KB per night.** Prevents: a clustering or naming mistake becoming a corpus-wide event instead of a one-map event Jason will see. Highest leverage guardrail per line of code in the whole design.
- **The SQL eligibility predicate gates admission**, journals and ingest corpora excluded, allowlist not denylist. Prevents: `dispatch-performance-log` generating twenty noise maps on night one and every night after.
- **A cost accumulator with a hard per-night ceiling.** Prevents: the one failure mode a metered loop has that a prepaid one does not — an unattended retry storm billing real money overnight. talos deferred token and cost caps because its production lane is prepaid open weights; that reason does not transfer.
- **Assert prompt-cache hits.** Read `cache_read_input_tokens` on every response and alarm if it stays zero across same-prefix turns. Prevents: a silent invalidator — a timestamp in the prompt, a `HashMap` iteration order — quietly multiplying the bill, which an unattended loop cannot notice the way an interactive user would.
- **Never re-execute an interrupted write on resume.** Pair `ToolCallStarted` to `ToolCallResult` by `call_id`; an unmatched start gets a synthesized error, never a retry. Prevents: a duplicate pointer append when the process dies between the POST and the log write.
- **Assert at startup that the working directory is NOT a git repo.** Prevents: the silent total failure where an HTTP-only agent leaves the tree unchanged, `finish(done)` is rejected by the change-evidence leg on every attempt, and every run burns its full iteration budget before failing. The fail-open on `Unobservable` is what makes the loop work; a stray `.git` turns it into a fail-closed.
- **Kill switch env var defaulting OFF**, same shape as `KB_LISTENER_ENABLED`. Prevents: a bad night continuing to be a bad night while Jason is asleep on a train.
- **Never survey through `/api/kb/get`.** That route is the only writer of `last_accessed`, which is simultaneously the sole pull-through read signal (541 of 3,228 entries) and the decay anchor, `max(created_at, last_accessed)`. Prevents: a nightly survey destroying the signal it depends on and resetting decay corpus-wide.
- **Never trigger on `search_events`, `agent_feedback`, `graph_edges.created_at`, or raw write volume.** Reasons above.
- **Every version carries a `change_reason`** naming the trigger and the evidence. Prevents: an un-auditable diff a month later.

**Expensive, and worth it:**

- **The append-only diff validator.** Enforcing test (1) mechanically — distinguishing "appended a bullet" from "rewrote paragraph two" — is real work. It is the thing that makes the whole unattended lane safe, and it is the reason the op vocabulary emits structured patches rather than bodies.
- **Optimistic concurrency.** Capture the map's `version` at proposal time; refuse the write if it moved. Prevents: the loop clobbering an edit Jason made between detection and write.
- **Churn brake.** A map with ≥K machine-authored versions in the trailing week goes to review instead of being edited again. Prevents: the slow oscillation that is invisible in any single diff. Requires the machine-version count, which requires the API key.

**Deliberately not mandatory:** a lease (only needed if a manual run can race the timer — add it when that becomes true), a run table, and a five-stage checkpointed DAG. Recovery is per-project replay of pure stages; idempotency comes from a UNIQUE on `(project, op, target_map, content_hash)` and from the fact that "detail entries with no owning map" *is* the cursor.

## How we would know it is working

Every metric that matters is demand-side and already instrumented. **Pointer coverage is not a success metric** — it is the loop's own output, so a loop that writes pointers moves it by construction. Track it as a progress bar, never as evidence.

**Primary: listener whisper rate and `vote-none` share, segmented by the candidate map's `contributor`.** The unanimous-3 Sonnet jury renders a relevance verdict on ~70 retrieval-reaching candidates per day — two orders of magnitude denser than consumption, and it is free. Today: 6 whispered of 151 decisions; 60 `vote-none` of the 72 that reached the jury. If machine-authored maps are rejected at a materially higher rate than human-authored ones, the loop is producing junk and we know within a week.

**The one blocker, and it must land first: `listener_decisions` stores `candidates_considered` as an integer and no ids.** Logging the candidate map ids and the whispered id is the cheapest instrumentation in this entire design space, it is what makes the program falsifiable, and it additionally gives us the retrieval-demand signal that should eventually *rank* the nightly worklist ("which projects' maps get retrieved as candidates from other projects' sessions"). The per-stage counters `n_retrieved` / `n_after_a` / `n_after_b` are already computed in `listener_routes.py` and discarded — persist them as columns too, so `rule-a` and `rule-b` attrition stops being inferred from a masked reason.

**Quiet-degradation metric: machine-map reversion rate** — the fraction of machine-touched maps a human subsequently reverts, substantially rewrites, or deactivates — reported unprompted, with an automatic pause of the unattended lane above a threshold. This is the only instrument that catches "the corpus looks maintained while degrading," which is the failure this design is most likely to produce: nobody reads maps directly, a degraded map produces no error and no failed test, and maps are decay-exempt (`confidence/decay.py:33` treats them as structural) so a stale map never self-reports. The cheap automated proxy is the jury segmentation above; the human sample is three machine-touched maps a week, sixty seconds each.

**Secondary: roster consumption for the project's own sessions.** Because rule A suppresses same-project maps from the listener, a new map in project X serves X's own sessions only through the roster channel. Roster consumption is 7 of 2,415 — diluted because roster pushes unconditionally — but segmented by project and by authorship it is the only readout of in-project value.

**Baseline caveat, stated honestly and then deliberately not acted on: the demand-side instrument is 34 hours old.** `listener_decisions` spans 2026-09-18 09:57 to 2026-09-19 19:40, and the detail-match retrieval path it measures shipped in commit a28cd0d. **An earlier draft of this document made a two-week accumulation window a prerequisite for building anything. That is cut, and the reason is a scale error the draft made about its own context.** This is one person's weekend home lab, the feature is roughly four hours of wall-clock work at dispatch rates, and the decisive evidence is already in hand: the map feature has existed for three months and covers 3.8% of the corpus, which is the finding. Manual maintenance does not work, and no amount of further measurement will make it work. Let the telemetry accumulate in the background — it is free and it will sharpen the ranking later — but do not gate the build on it. The instrument's job here is to catch the loop producing junk, which it does from night one on a per-map basis; it is not a permission slip.

## The smallest falsifying experiment

**Run the loop's backfill over three projects and read the maps it wrote.** At a measured $3.40 for the entire 16-project backfill, a three-project slice costs well under a dollar and completes in minutes, which makes "build it and look" strictly cheaper and faster than any proxy experiment. Read the maps. `photoqueue`, `camera-profiles` and `flickrasync` are the right slice — all active, all currently unmapped, and `photoqueue`'s clusters are already named from the ground work (Lightroom SDK/Lua, queue and rate-limit infrastructure, dismissal/telemetry, discovery scoring, multi-tenant bootstrap), which gives a direct read on whether the model's clustering agrees with a human's.

**The first gate is a human reading three maps, not a metric.** Does each map orient without holding facts, does every pointer resolve to something chunky and actually related, is the reading defensible? That is sixty seconds per map and it answers the only question that can kill the design — whether machine-authored maps are any good — with no waiting at all. A metric cannot answer it faster, and a metric that disagreed with the reading would lose.

**The jury telemetry is the follow-on instrument, and its prediction still needs to respect rule A.** The naive form — "author `photoqueue` maps, watch `photoqueue`'s `vote-none` rate fall" — is *wrong*: rule A drops `photoqueue`'s own maps from `photoqueue` sessions, so those 31 opportunities are structurally unaffected. The correct prediction is global and cross-project: the candidate pool available to every *other* project's sessions gains topical breadth, so the whisper rate should rise from ~4% (6/151) and the `vote-none` share of retrieval-reaching decisions should fall from ~83%, with the new maps appearing in the logged candidate ids. At ~100 decisions/day that reads within days, and it reads *while* the loop is running rather than before it is built.

**Kill and reshape conditions.** If the candidate ids show the new maps are *never retrieved as candidates* → the problem is retrieval/detail-matching, not map supply, and the nightly loop is the wrong build entirely. If they are retrieved and the jury rejects them at the same rate as the incumbents → maps do not convert and no quantity of supply helps; stop, and spend the effort on the jury or on the roster surface instead. If the whisper rate rises but consumption does not follow → we are manufacturing noise the agent ignores, and the program needs a quality bar before a volume bar. Only a rise in whisper rate *and* a non-trivial consumption rate justifies the machinery.

Second, cheap, run alongside: **hold a fixture set of the three projects' clusters and re-run the naming step on a cheap lane to see whether it agrees with Sonnet.** Every position in the debate asserted that naming is frontier work, on the strength of one worked example — it is plausible and untested. But note the stake has shrunk: with the loop priced at ~$5/month, this is no longer the difference between pennies and dollars, it is a quality comparison with a fixture set attached. Run it because a fixture set is worth having, not because the bill demands it.

## Phased rollout

**Phase 0 — the gates and the instrument (days, blocked only on a deploy window).** All the cheap guardrails above: orphan check on update, full-body automated writes, edge-set superset invariant, server-side lint for the machine principal, machine API key, never-deactivate. Plus the candidate-id and per-stage-counter columns on `listener_decisions`. Plus two one-line repairs: `recommend-maps.workflow.js:23`'s false claim, and `chmod 644` on that file. Plus the repair pass over the 23 maps whose enrichment edges were stripped (and an audit for other entries with `version > 1` and zero LLM edges). **This ships regardless of every decision below** — it fixes a live data-destruction bug and makes every other design in this document safe. It needs a `./deploy.sh`, which is blocked while dispatch work is in flight, so it queues behind the current wave.

**Phase 1 — Loop 0, the capture-time nudge.** ~30 lines in `kb_store`'s existing advisory seam plus one anti-join and one kNN. No scheduler, no state, no review surface. This is the piece that most directly answers "it can't be a thing I have to remember," because it fires on the action rather than on a clock, and it stops the deficit growing while we decide about everything else.

**Phase 2 — the loop, run by hand over three projects.** The SQL eligibility predicate, pocket detection, the closed op vocabulary, code-composed map bodies, the additive-only write path, and a `--project` flag so it runs on demand. No timer yet. This is the same binary Phase 3 schedules; the only thing missing is the clock. Under a dollar to run, minutes to complete, and the output is three projects' maps for you to read. **This replaces the first draft's "one afternoon of hand-authoring plus two weeks of waiting" — the loop is now cheaper to build and run than the manual proxy it was standing in for.**

**Phase 3 — put it on a timer and let the backfill drain.** The full 16-project backfill at ~$3.40, then the nightly cadence, with the cost accumulator, the per-night caps, the churn brake and the kill switch armed. **State is exactly one table** — the cluster/decline ledger, keyed on member-set overlap rather than label, because labels drift and it is the only artifact in this design that grows monotonically and cannot be recomputed. No run table, no lease, no five-stage DAG. `cleanr` (194 entries, zero maps) drains here like everything else rather than needing a separate supervised wave; the measured cost is what collapses that distinction.

**The cut line, stated as a reason rather than a preference:** the gates are cheap, verified, and unconditionally required regardless of everything downstream; the capture-time nudge is 30 lines and answers the literal complaint; Phase 2 is the falsifying experiment *and* the build, because pricing it revealed they are the same act. What the first draft treated as the expensive judgment-laden endgame — the nightly loop — turns out to cost $5/month and to be mostly SQL plus one inference per unit. The expensive part was never the loop. It is the curation of the op vocabulary and the canonical map form, which is where the domain knowledge lives and is exactly where effort should go.

## Non-goals

This does not regenerate map bodies, ever, for human-authored maps. It does not relax the map-purity lint — it promotes it. It does not touch `project_ref` assignments, deactivate anything, remove a pointer, or write to `NULL`-project entries. It does not run general project-wide clustering with a chosen `k`. It does not attempt to map journals or ingest corpora (about two-thirds of the corpus), and it explicitly has no answer for `harness-design` — a 71-entry temporally ordered session journal with a reading order and no topical partition, which is simultaneously one of the loudest attention signals in the KB and the one project the eligibility predicate classifies wrongly. It also never writes its own eligibility override. It does not run frontier inference inside the kb-service event loop. It does not extend to the team or user2 KBs in v1. And it does not build a review queue that blocks the unattended lane.

## Decisions for Jason

**1. Runner: purpose-built loop binary, or a Claude Code harness?** **Recommendation: a purpose-built loop binary on the kb-service host, consuming the `harness` crate as a library.** Claude Code does not run well on an 8GB Pi 4, and once the read path is pre-fetched this loop needs no repo clone, no workflows directory, no MCP server and no general tool surface — only outbound HTTPS to two endpoints. That makes the natural host the Pi already running kb-service, where the machine key and DB pool live. The build-vs-extend sub-question is now **settled by reading the code**: the tool registry is a caller-supplied parameter, a run works fine with no git repo, and `harness` is a genuine library crate with four examples of external consumers. This is a tool set plus a gate adapter.

**1b. Where does that binary's code live?** The real remaining fork, and the only one blocking decomposition. **Recommendation: a new crate in the `harness-design` workspace**, because it can then take `harness` as a path dependency and — more importantly — inherit talos's existing cross-compile and prebuilt-binary distribution to the Pis rather than standing up a second aarch64 release pipeline. The honest counter-argument is that `harness-design` is a research repo and this is personal-kb product code, so the alternative is a standalone repo depending on `harness` by git rev, paying for its own release path. A Rust binary inside `personal-kb-web-service` is the third option and the weakest: it would ride the right `deploy.sh` but put a Rust toolchain in a Python repo whose deploy currently just pulls and restarts.

**2. Autonomous `create_map` on night one?** **Recommendation: yes, behind the one-per-project/three-per-KB cap.** Creation is additive, cannot destroy human prose, is trivially revertible, and is where the measured value is. The cap converts every mistake into a single map you will see in the digest. A review gate on creation is the design we already have, and it produced 27 maps in three months.

**3. Does a decline ever expire?** **Recommendation: permanent, with one escape — reopen when the cluster's member set doubles.** That respects your attention as the scarce resource while preventing a cluster declined at 20 entries from being suppressed forever at 200.

**4. Hard lint: machine principal only, or everyone?** **Recommendation: machine only.** Your two best maps already exceed the 1,500-char advisory. Hard-gating your own authoring changes your ergonomics to fix a problem you do not have.

**5. Authorship-tiered prose editing?** **Recommendation: yes.** A blanket "never regenerate" over-protects a machine-created map with no glosses, no trap warnings and nothing to lose. Freeze human-authored bodies permanently; let the loop own the ones it wrote. This needs only the API key from Phase 0.

**6. Rule A — keep, or soften to a ranking penalty?** This is a product call about what the listener is *for*. **Recommendation: keep it, and accept the consequence** — the roster already pushes a project's own maps at session start, so the listener's job is cross-project surprise, and the design above ranks nightly work by cross-project retrieval demand rather than by the project's own attention. But know that this makes the in-project value of a new map measurable only through the diluted roster channel. (Your in-flight plural-whisper change helps here independently: with more than one map per whisper, additional good maps stop competing winner-take-all for a single slot, so each marginal map is worth more.)

**7. Loosen the unanimous-3 jury before or after building supply?** **Recommendation: after, and only if Phase 2 says supply converts.** Supply work and gate work compete for the same measurement window and running both makes each uninterpretable. Do supply first because it is the thing you asked for; the jury is one config change you can make any time.

**8. `cleanr`: nightly loop, or Phase 3 wave?** **Recommendation: Phase 3.** It is the largest supply gap in the KB and has zero measured demand — zero listener opportunities, zero whisper sessions. Every position called it the biggest gap on supply grounds; on the only metric that connects a map to an outcome it is currently worth nothing. Sweep it in the finite wave, do not distort the nightly predicate for it.

**9. `harness-design`: mark unmappable, or invent a reading-order map shape?** **Recommendation: mark it `journal` in the override table for now and revisit.** Note that this is one of the ~5 refs the SQL predicate gets *wrong* — 71 entries, zero ingested, 66 distinct title prefixes, so it passes every code gate as a subject area. Its shape (a dated session log with a reading order) genuinely has no topical partition, and inventing a new map genre is a bigger design question than this document should settle. But it is also the loudest attention signal in the KB, so marking it away is a real gap dressed as a decision, and you should know that.

**10. Nightly budget and the per-project write cap.** **Priced: ~$3.40 for the full backfill, ~$0.17/night, ~$5/month on Sonnet** (see "What it costs"). The first draft said "I cannot price this" and recommended structural caps in lieu of a dollar budget. **Recommendation: build both.** Keep the structural caps — one new map per project per night, three per KB — because they are what converts a clustering mistake into a one-map event rather than a corpus-wide one, and cost was never the thing they were protecting against. But add the dollar ceiling too, because a metered loop has a failure mode a prepaid one does not: an unattended retry storm at 3am. The ceiling should sit far above the $0.17 expected spend, so that tripping it is unambiguously a bug signal rather than a throttle.

## Open questions we could not settle

**Is the binding constraint coverage or relevance?** 145 of 151 requests resolved to a pointer-reachable owning map at 3.8% coverage, which means a map was *reachable* — not that it was *right*. The 60 `vote-none` declines could be the jury correctly rejecting maps found via weak detail matches, which is a coverage-of-the-right-subject-areas problem wearing a relevance costume. **Resolved by:** Phase 2's candidate-id telemetry — whether the new maps get retrieved at all, and whether the jury treats them differently from the incumbents. Read it while the loop runs, not before it is built.

**Can a cheap lane name subject areas?** Every position asserted naming is frontier work on the strength of one worked example. **Resolved by:** re-running Phase 2's naming step on a cheap lane against the same fixture set and comparing. Lower stakes than it looked — the loop is $5/month on Sonnet, so this is a quality question, not a budget one.

**Does dropping reasoning blocks hurt on Anthropic backends?** talos's compaction is Ollama-only by construction (it gates on a backend advertising a numeric context limit), which *moots* rather than answers whether tier-1 compaction is safe under Anthropic's thinking-block replay rules — blocks must be passed back exactly as received. This design does not build compaction at all, so the question stays moot here. It returns the moment anyone wants a loop on this backend that does.

**Where is the Jaccard threshold for cluster identity?** The overlap *shape* is verified (17 details with two owning maps, 4 with three or four, kb-03215 and kb-03217 genuinely in both VPN and DNS), but 0.5 is invented. Too high thrashes; too low permanently suppresses real clusters. **Resolved by:** logging near-misses in the 0.3–0.5 band from night one and tuning from real data rather than guessing forever.

**Is there a safe mechanism for improving an existing human-authored map?** Everything in this design bans it, and everything in this design concedes that is where the craft lives — the trap warnings, the reading order, the glosses better than the target entries' own titles. A shelver is not an editor. **Resolved by:** nothing we currently know how to build. It is a standing frontier, and it is the part of your complaint this design does not fix.

**Does the digest actually get read?** The design deliberately puts nothing blocking behind it, so a never-read digest degrades to "the additive lane ran and nobody checked." **Resolved by:** the reversion metric with an auto-pause — the one control that works whether or not anyone is looking.

**Is the `photoqueue`-class project the right target at all, or does mapping follow attention with a lag we cannot see?** The activity signal's discriminating range is 1 to 4 distinct sessions and it reorders within a day. **Resolved by:** the telemetry, read as it accumulates — and note this only ever mattered for *ranking* the worklist. At 16 eligible projects and $3.40 to do all of them, there is no scarcity to ration, so a wrong ranking costs an ordering, not an outcome.
